# API routes still gated by a ROLE ARRAY rather than a permission.
#
# These are NOT a security hole. requireAuthWithRole re-reads StaffMember with
# isActive on every request, so they revoke correctly; what they cannot do is
# answer "what can a DESIGNER do?" without a grep, which is the whole reason the
# permission layer exists.
#
# Each one is listed because the semantically correct permission would CHANGE who
# may call it -- in one direction or the other. Both are wrong to do silently:
#   widens   the permission admits a role the route excludes today
#   tightens the permission excludes a role the route admits today
#
# Converting one is a deliberate decision about access, not a refactor. Make it,
# adjust the grant or pick a different permission, and delete the line.
#
# __tests__/apiRolePermissionRatchet.test.ts holds the count: this list may
# shrink, never grow.
#
